# 04 — Pricing engine

The engine is the owner's specification, implemented and tested in `docs/reference/pricing/`:

| File | What it is |
|---|---|
| `types.ts` | Input, config, output and error types |
| `dates.ts` | Civil-date helpers (no clock reads) + `londonToday()` |
| `config.default.ts` | Pricing config v1 (the owner's numbers) |
| `engine.ts` | The algorithm: `computeQuote`, `priceForSlot`, `computeStaticBreakdown`, `buildCalendar`, `slotPricePence`, `validateConfig` |
| `engine.test.ts` | Hand-calculated checks (12 tests, all passing) |
| `vectors.json` | 8 golden vectors × 84 slot prices, generated by `generate-vectors.ts` |

**Phase 2 job:** port these files into `packages/pricing/src/` (extensionless imports), port the tests to Vitest, add the golden-vector test and property tests, enforce 100% coverage. Nothing about the arithmetic changes.

## 1. Rules

1. `@sv/pricing` is the only code that computes a price. Web API, booking verification, reschedules, admin re-pricing, the admin simulator, SEO example prices and "from" prices all call it.
2. The engine is pure: no clock, no network, no randomness, no dependencies. Callers pass `today` (London civil date).
3. Config comes from the database (`PricingConfigVersion` with status ACTIVE). `DEFAULT_PRICING_CONFIG` is only the seed for v1 and test fixture.
4. A quote records the config version, `today`, distance and every input it priced. Re-running the engine on those reproduces the same pence, on every platform.

## 2. Algorithm (owner spec)

```
staticSubtotal = service base × variant multiplier
               + distance cost
               + pickup floor cost + dropoff floor cost
               + inventory cost
               + access cost (carry + narrow + permit)
               + add-on cost
slotPrice      = round( staticSubtotal × urgency × weekend × peakMonth × endOfMonth × slot )
```

Output: 28 days × 3 slots (MORNING, AFTERNOON, EVENING), day 0 = today in Europe/London.

| Component | Rule (defaults) |
|---|---|
| Service base | house removals £120, furniture £60, storage £45, office £150, man and van £45, student £80, IKEA £70, piano £200, same-day £55 — × variant multiplier |
| Distance | billable = max(0, miles − 5). First 20 billable miles at £1.50; every billable mile after 20 at £1.50 × 0.85 |
| Large-inventory distance | when the load is "large" and `largeInventory.distance` is set, those rates replace the standard ones (default: not set) |
| Floors (each address) | floor × £8, × 1.5 when there's no lift. Ground = 0 |
| Inventory | items × £2 + m³ × £6 |
| Large inventory | when item count > 4 **and** volume ≥ 1 m³: max(£75, items × £4 + m³ × £12) |
| Access | carry: (metres − 10) × £0.50 when over 10 m; narrow access £25; permit/controlled-parking zone £20 |
| Add-ons | £18 per extra helper (max 3); packing £35; assembly £25 |
| Urgency | today ×1.4, tomorrow ×1.2, day after ×1.1, else ×1 |
| Weekend | Saturday/Sunday ×1.15 |
| Peak months | June, July, August ×1.1 |
| End of month | final 3 days of the month ×1.08 (Feb: 26–28, or 27–29 in leap years) |
| Slot | morning ×1.05, afternoon ×1.0, evening ×1.1 |

There is **no weather factor**. Weather never affects price.

## 3. How customer answers become engine input

| Customer answers (06-booking-flow) | Engine field |
|---|---|
| Service card | `service` |
| Property size / piano type / office size / storage direction / student type | `variant` (services with one variant send `standard`) |
| Pickup + dropoff addresses → Mapbox driving route | `distanceMiles` = metres ÷ 1609.344, rounded to 2 dp **once**, stored on the quote. |
| Floor picker at each address (Basement → 1, Ground → 0, 1st → 1 …) | `pickup.floor`, `dropoff.floor` |
| "Is there a lift?" (shown only when floor ≥ 1) | `hasLift` |
| Items picker (catalogue item or custom size) | `inventory[]` with `unitVolumeM3` **snapshotted** from the catalogue at quote time |
| Per-address access answers | job-level `access` (§5) |
| Extra helpers / packing / assembly | `addons` |

Custom item sizes (when the customer can't find an item): Small 0.1 m³, Medium 0.3, Large 0.8, Extra large 1.5 — `config.customItemSizes`, versioned with the rest of pricing. The quote service converts them to `unitVolumeM3`; the engine never sees sizes, only volumes.

## 4. Precision rules (already implemented in the reference)

- Config is in pounds; the engine converts each value to pence once.
- Every component is rounded half-up to a whole penny; the subtotal is the exact integer sum, so every breakdown line shown to a customer adds up to the subtotal.
- Slot price = subtotal pence × the five multipliers in the spec's order, rounded half-up to a penny.
- Floating-point noise is removed with `Number(x.toPrecision(15))` before rounding (148.00499999… becomes 148.005 → £148.01).
- Inventory volume is normalised to 4 dp before comparing with the 1 m³ threshold (0.7 + 0.3 counts as exactly 1).

## 5. Access: per address in the UI, job-level in the engine

The spec prices access once per job. Drivers need to know *where* the problem is, so the UI asks per address and the server derives the engine input:

| Engine field | Derived from per-address answers |
|---|---|
| `carryMetres` | the **longer** of the two carry distances |
| `narrowAccess` | true if **either** address has narrow access (charged once) |
| `permitZone` | true if **either** address is in a permit/controlled-parking zone (charged once) |

Both are stored: per-address detail in `Quote.accessDetail` / `Booking.accessDetail` (shown to drivers and admins), job-level values inside `pricingInput`. This is owner decision **P3** (§7).

## 7. Owner decisions (neutral defaults; approve in Admin → Pricing)

| # | Question | Default (changes no prices) | Where to change |
|---|---|---|---|
| P1 | Variant multipliers (studio…4+ bed, office sizes, piano types, storage direction, student type) | all 1.0 | Pricing → Services |
| P2 | Separate per-mile rates for large loads | not set (standard rates) | Pricing → Distance |
| P3 | Per-address access → job-level | longest carry; narrow/permit once | fixed in code (change = new decision) |
| P5 | Same-day service shows only today's remaining slots | yes | fixed in code (change = new decision) |
| P6 | Basement counts as one floor of stairs | yes | fixed in UI mapping |

Grand pianos, baby grands and offices of 16+ desks route to **manual quote** by default (`manualQuote: true` on the variant).

**Launch gate:** `PricingConfigVersion.approvedByOwner` must be true on the ACTIVE version. The Admin app's *Approve pricing* screen shows P1–P6, the worked examples recomputed with the live config, and requires the OWNER role.

## 8. Where the engine is called

| Caller | Function | Config | `today` |
|---|---|---|---|
| Quote stream | `computeQuote` | ACTIVE | `londonToday(now)` |
| Booking creation — quote still valid | `priceForSlot` (verification against stored calendar) | quote's version | quote's `today` |
| Booking creation — quote expired | `priceForSlot` | ACTIVE | `londonToday(now)` → if different from what the customer saw: `409 PRICE_CHANGED` |
| Reschedule (customer or admin) | `priceForSlot` for new date/slot | ACTIVE | now |
| Admin edits inputs on a booking | `computeStaticBreakdown` + `slotPricePence` with the booking's **stored slot multipliers** | booking's version | n/a |
| Admin simulator | `computeQuote` | DRAFT or ACTIVE (selectable) | any date picked |
| SEO example prices / "from" prices | `computeQuote`, min over capacity-available slots | ACTIVE | build/revalidate day |

**Admin edits rule:** extra items or changed access after booking are priced at the rates and date multipliers the customer booked with — new subtotal × the booking's stored multipliers. The difference becomes an extra charge (payment link) or a refund. A test asserts that re-pricing an unedited booking returns exactly its `totalPence`.

## 9. Quote service (server orchestration around the engine)

`src/server/services/quote.ts` — called by `POST /api/v1/quotes`:

1. Parse request (`QuoteRequestSchema`). Snapshot item volumes from the `Item` table (ignore client-sent volumes).
2. Route: Mapbox Directions `driving`, `steps=true`, `overview=full` — cached in-memory per instance and in Redis for 24 h by rounded coordinates. If any step has `mode === "ferry"` → manual quote reason `FERRY_ROUTE`. Verify the ferry `mode` field against the current Mapbox Directions docs and cover it with a fixture test.
3. Service area: per `operations.serviceAreaRule` using the address's postcode area (`AB DD DG EH FK G HS IV KA KW KY ML PA PH TD ZE` are Scottish; `TD15` and other English districts inside TD/DG are excluded by district list in `@sv/contracts/address`). Outside → `OUTSIDE_SERVICE_AREA` (no quote, friendly message + phone). Cross-border allowed only if `operations.crossBorderMoves`.
4. Distance > `maxInstantDistanceMiles` → manual quote reason `LONG_DISTANCE`.
5. `computeQuote(input, activeConfig, londonToday(now))`.
6. Job size: from the inventory volume and `operations.jobSizeRules` (03 §6.1) → `capacityUnits`, `blocksSlots` (stored on the `Quote` and copied to the `Booking`; not part of pricing).
7. Availability overlay (06-booking-flow §6.4): capacity (job-size aware), lead time, closed dates, same-day rule → each slot `{ available, reason?, lastOne }`.
8. Persist `Quote` (status ACTIVE, `expiresAt = now + quoteValidityMinutes`).
9. Emit stream events (06 §5).

## 10. Admin pricing management

- Versions: DRAFT → (validate + preview) → ACTIVE; previous ACTIVE → ARCHIVED, atomically (partial unique index guarantees one ACTIVE).
- Editing creates a DRAFT copy of ACTIVE. The simulator shows the same scenario priced by ACTIVE and DRAFT side by side, with per-line differences.
- Publish requires `validateConfig()` to return no problems, a typed confirmation, and OWNER or ADMIN role. Publishing records who/when, audits, revalidates `pricing` pages, and affects **new quotes only** — existing quotes and bookings keep their version.
- Approve pricing (OWNER only) sets `approvedByOwner` on the active version.

## 11. Tests (Phase 2 and later)

- Reference tests ported 1:1.
- Golden vectors: every one of the 8 × 84 prices, plus each breakdown, must match exactly.
- Property tests (fast-check, 1,000 runs each): price never negative; adding an item never lowers price; more miles never lowers price; afternoon ≤ morning and ≤ evening under default config; output always 28 × 3; `priceForSlot` always equals the calendar entry.
- Coverage: 100% lines and branches for `packages/pricing`.
- Integration (Phase 6–7): stored quote → booking verification reproduces the stored calendar price; modified `expectedTotalPence` → 409.

## 12. Lessons built into this design

The previous system had four pricing defects. Each is now impossible by construction:

| Defect | Prevention |
|---|---|
| Weather pricing existed in config but was never applied | No weather factor exists; config is a typed schema validated on save |
| Quote tokens were optional and didn't cover all inputs | Quotes are server records; bookings must reference one; prices are re-verified from stored inputs |
| Access surcharges weren't saved, so admin re-pricing used zeros | Every input is persisted on quote and booking; repricing an unedited booking must equal `totalPence` (tested) |
| Admin simulator used stale category names | Simulator imports `@sv/pricing` types; a wrong name is a compile error; simulator runs the golden vectors in CI |
